# 模块二库存规划进度 · 产品说明

对应界面：浅色实时进度台（无对话）。数据来源：规划服务 SSE 事件流（`started` / `thinking` / `step` / `result` / `end`）。

本文只约定 **给业务用户看什么**、**什么只给编排器/前端消化**。字段名按事件 payload 原样列出。

---

## 1. 产品原则

1. 用户要看到的是「现在在做什么、为什么、做成了什么」，不是协议本身。
2. **step = 工具执行**（可成功可失败，推进业务流程）。**thinking = 推理**（不改世界状态）。两类必须分开展示。
3. 同一语义只呈现一次。`headline` / `summary` 与 `title` / `detail` 重复时，只取给人看的那一份。
4. 空值、占位、心跳、状态机代码默认不进主界面。
5. `visible=false` 的事件整条丢弃，不进入 UI 状态。

---

## 2. 事件信封（每条 SSE 都有）

| 字段 | 类型 | 判定 | 呈现规则 |
|---|---|---|---|
| `event` | 枚举 | 过程 | 决定渲染形态，不把英文事件名画出来 |
| `id` | 字符串 | 过程 | SSE 序号，仅用于去重/排序 |
| `t` / 到达时刻 | 毫秒 | 过程 | 换算成已用时 `mm:ss`，不展示原始时间戳 |

---

## 3. `started` · 开跑

| 字段 | 判定 | 呈现 |
|---|---|---|
| `headline` | **呈现** | 页头主标题。例：开始规划模块二库存 |
| `detail` | **呈现** | 页头说明。例：改单后重新分配库存… |
| `phase` | **呈现** | 元信息。例：阶段 MKE |
| `operatorType` | **呈现** | 元信息。建议映射文案：`updateOrder` → 改单分配 |
| `runId` | **呈现（缩写）** | 便于对账；界面截成前 8 + 后 4，完整值仅复制/日志 |
| `summary` | 过程 | 本轮与 `detail` 同文，不单独占位 |

运行态由后续事件推导，不来自本包：规划中 / 已完成 / 待命。

---

## 4. `thinking` · 推理

先看 `role`，再决定画在哪。

### 4.1 编排心跳 · `role = orchestrator`

几乎每步结束后都会再打一条，文案长期是「正在规划本阶段库存分配」。

| 字段 | 判定 | 呈现 |
|---|---|---|
| `detail` | **弱呈现** | 仅运行中：顶栏一条闪动状态，**不进步骤列表** |
| `status` | 过程（驱动动画） | `running` 闪动；`done` 顶栏收起 |
| `title` / `headline` | 过程 | 与「规划中」重复 |
| `summary` | 过程 | 与 `detail` 重复 |
| `seq` | 过程 | 心跳序号，界面不展示 |
| `visible` | 过程 | 过滤开关 |
| `role` | 过程 | 用来分流，不把 `orchestrator` 当标签展示 |

### 4.2 模型推理 · `role = demand_lines.system`（及其他非 orchestrator）

这是大模型真正的决策说明，嵌在**当前 step 下方**的「推理」块。

| 字段 | 判定 | 呈现 |
|---|---|---|
| `detail` | **呈现** | 推理正文。running 用闪动，done 用静态 |
| `title` | **呈现（兜底）** | `detail` 为空时用 title |
| `status` | **呈现（形态）** | 图标/闪动，不写英文 |
| `role` | **弱呈现** | 推理块次要标签，便于区分是哪个子系统在想 |
| `headline` / `summary` | 过程 | 与 title/detail 重复 |
| `visible` | 过程 | 过滤开关 |

禁止把 thinking 画成又一条工具步骤。

---

## 5. `step` · 工具执行

一条工具从 `running` 到 `done`/`error` 是**同一行**的状态更新，不是两行。

### 5.1 行头（用户主信息）

| 字段 | 判定 | 呈现 |
|---|---|---|
| `title` | **呈现** | 步骤主文案。running：「正在计算物料需求」；done：「已算清物料需求」 |
| `status` | **呈现（形态）** | 转圈 / 勾 / 叉，不写 running/done |
| `detail` | **呈现** | 完成后的一句话结果；running 且空则不占行 |
| `tool` | **弱呈现** | 次要技术名（下划线改空格）。给能对上系统的人看，不是主标题 |
| `source` | **条件呈现** | 见 5.3 |
| `headline` | 过程 | 本轮恒等于 `title` |
| `summary` | 过程 | 本轮恒等于 `detail` 或 `title` |
| `visible` | 过程 | 过滤开关 |

### 5.2 `stage` · 过程字段（状态机）

`PREPARED` → `REQUIREMENTS_COMPUTED` → `TASKS_RANKED` → `ACCESS_RESOLVED` → `LINES_RANKED` → `PURCHASE_COMPUTED` → `TOP_UP_DONE`

这是编排器内部游标，**不是业务文案**。后半段多步共用 `TOP_UP_DONE`，直接展示会误导「还在加锁」。

**产品约定：主界面不展示原始 stage 代码。** 进度用步骤列表 + 顶栏进度条表达。若运维需要，放进调试层。

### 5.3 `source` · 策略来源

| 值 | 判定 | 呈现 |
|---|---|---|
| `fallback` | **呈现** | 徽章「规则回退」，并提高该步告警权重 |
| `default_policy` | **弱呈现** | 徽章「默认策略」 |
| `none` | **弱呈现** | 结合 tool 译成业务句，如「无需加锁」 |
| `""` | 过程 | 未决，不展示 |

### 5.4 `preview` · 结构化结果（只抽业务量）

running 时多为 `{}`，空对象不展示。

| 子字段 | 出现在 | 判定 | 呈现 |
|---|---|---|---|
| `taskCount` | compute_requirements | **呈现** | n 张任务 |
| `poolCount` | resolve_inventory_access | **呈现** | 专用池 n |
| `unmetCount` | plan_upstream / get_unmet_demands | **呈现** | 缺口 n |
| `itemCount` | propose_top_up | **呈现** | 加锁 n |
| `passed` | validate_plan | **呈现** | 校验通过 / 未通过 |
| `submitted` | submit_target_plan | **呈现** | 已提交 |
| `source` | 多步 | 同 5.3 | 与行级 source 去重，只显示一次 |
| `lineCount` / `waveOne` / `waveTwo` | rank_demand_lines | **呈现（非零）** | 需求行、第一波、第二波；全 0 可只靠 detail |
| `module1Count` / `purchaseCount` | plan_upstream | **呈现** | 模块一转交 n、采购建议 n |
| `orderedTaskIds` | rank_tasks | 过程 | 内部任务 ID 列表，无名称映射则不铺开 |
| `module1Materials` | plan_upstream | 过程 | 物料明细数组，主界面只用数量 |
| `errorCount` | validate_plan | 过程 | 已被 `passed` + detail 覆盖 |
| `runId` | submit_target_plan.preview | 过程 | 与 started.runId 重复 |
| `stage` | get_unmet_demands.preview | 过程 | 与 step.stage 重复 |

---

## 6. `result` · 终态

| 字段 | 判定 | 呈现 |
|---|---|---|
| `data.actions` | **呈现数量** | 「动作 n」；完整动作体默认不展开 |
| `data.unmetDemands` | **呈现数量** | 「缺口 n」；明细默认不展开 |
| `data.warnings[]` | **呈现** | 每条：`code` + `message`；`severity` 映射颜色（warning/error/info） |
| `data.runId` | 过程 | 与页头 runId 重复 |
| `code` | 过程 | `200` 映射为成功，不展示数字 |
| `message` | 过程 | `"success"` 不展示 |

---

## 7. `end` · 收流

| 字段 | 判定 | 呈现 |
|---|---|---|
| `status` | **映射呈现** | `COMPLETED` → 已完成。不写英文枚举 |
| `eventCount` | 过程 | 协议计数。主界面可用步骤条代替；调试层可显示「n 条事件」 |

---

## 8. 界面结构（与字段对应）

```text
页头
  headline / detail          ← started
  状态徽章 + 已用时          ← 由事件流推导（过程字段合成）
  phase / operatorType / runId缩写
  进度条                     ← t / 总时长（过程合成）
  编排推理一行               ← orchestrator.detail（仅 running）

步骤列表（每个 step 一行）
  状态图标                   ← status
  title
  tool（弱）
  source 徽章（条件）
  preview 业务量徽章
  detail
  推理块                     ← 非 orchestrator 的 thinking.detail

结果
  动作数 / 缺口数 / 告警列表 ← result.data
```

## 9. 工具步骤对照（本轮日志）

| 顺序 | tool | 用户应看到的事 | 完成后关键呈现字段 |
|---|---|---|---|
| 1 | compute_requirements | 计算物料需求 | title, detail, taskCount |
| 2 | rank_tasks | 排出抢货顺序 | title, detail, source |
| 3 | resolve_inventory_access | 确认专用库存范围 | title, detail, poolCount, source |
| 4 | rank_demand_lines | 主料/辅料波次 | title, **模型推理**, source=fallback 时告警 |
| 5 | resolve_inventory_access | 再次确认可用范围 | 同 3 |
| 6 | plan_upstream | 按序分配库存 | title, detail, 转交/采购/缺口数量, **模型推理** |
| 7 | propose_top_up | 剩余库存是否多锁 | title, detail, itemCount, source |
| 8 | get_unmet_demands | 查看缺口 | title, detail, unmetCount |
| 9 | validate_plan | 校验规划 | title, detail, passed |
| 10 | submit_target_plan | 提交 | title, detail, submitted |

## 10. 一句话清单

**必须呈现**

- 开跑：`headline`、`detail`、阶段、操作类型、runId 缩写、运行状态、已用时
- 步骤：`title`、`status` 形态、非空 `detail`、业务 preview（任务数/池/缺口/加锁/校验/提交）、异常 `source`（规则回退）
- 推理：非编排器的 `detail`（及空 detail 时的 `title`）
- 结果：动作数、缺口数、告警 code + message

**过程字段（协议/状态机/重复项，主界面不直接展示）**

- `event`、`id`、原始 `t`、`visible`、`seq`
- `headline`、`summary`（与 title/detail 重复时）
- `stage` 及 preview 内重复的 `stage` / `runId`
- 空 `preview`、内部 ID 列表（`orderedTaskIds`）、明细数组（`module1Materials`）
- `result.code` / `result.message`、`end.eventCount` 原始值
- orchestrator 心跳的 title/headline/seq（只保留 running 时一条 detail）
