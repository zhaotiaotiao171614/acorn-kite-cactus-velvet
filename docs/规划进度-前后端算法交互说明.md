## 0. 产品形态（前端必须遵守）

1. 界面是**一条时间线**。`started` 与 `step` 使用**同一套节点模板**，不把 `started` 钉在表头。
2. **没有**固定在底部的结果区。`result` 事件前端收了也不画节点。
3. 节点 = 一次「开跑」或一次「工具调用」的生命周期（running → done/error），不是每一条 SSE 一行。
4. `thinking` 不是节点。编排器心跳只在**运行中**出现在时间线末尾；模型推理嵌在**当时正在跑的 step 节点内部**。

```text
[规划中/已完成]  00:47
────────────────────────────────
● 开始规划模块二库存          ← started 节点（与 step 同模板）
● 已算清物料需求              ← step 节点
● 已确定抢货顺序
● … 正在跑的 step
    ┌ 推理 demand_lines.system ┐  ← 仅非 orchestrator 的 thinking
    └ …模型正文…               ┘
○ 推理 orchestrator            ← 仅运行中、不入库、完成后消失
```

## 1. 通道约定

| 项 | 约定 |
|---|---|
| 协议 | SSE。每条：`event=<名>` + JSON `data` |
| 事件名 | `started` \| `thinking` \| `step` \| `result` \| `end` |
| 顺序 | 必须按发生顺序推送。前端按到达序 reduce，不重排 |
| 可见性 | `visible === false` 的 `thinking`/`step` **整条丢弃**，不建节点、不更新节点 |
| 幂等 | 同一 `tool` 在 `status=running` 期间的后续 `step`（同 tool）是**更新当前节点**，不是新节点 |

后端只转发，不改语义。算法是字段的唯一生产者。

## 2. 节点是什么、何时新建

### 2.1 新建节点的唯一入口

| 事件 | 是否新建节点 | 条件 |
|---|---|---|
| `started` | 是，立刻 1 个 | 本 run 第一条业务事件。`kind=started`，`tool` 固定写成 `"started"` |
| `step` 且 `visible=true` | 是，当且仅当不满足「合并」 | 见 2.2 |
| `thinking` | 否 | 见第 5 节 |
| `result` | 否 | 前端可存快照，**当前 UI 不渲染** |
| `end` | 否 | 只把页头状态改成「已完成」，并撤掉编排器心跳 |

### 2.2 step 合并规则（算法必须成对发 running/done）

记时间线最后一个节点为 `last`。

**合并进 `last`（不新建）当且仅当同时成立：**

1. `last.tool === data.tool`
2. `last.status === "running"`
3. 本条是该 tool 的收尾（通常 `status` 为 `done` 或 `error`）

合并时覆盖：`title`、`headline`、`status`、`stage`、`source`（空串不覆盖已有值）、`preview`（浅合并）、`detail`（空串不覆盖已有值）。

**新建节点当：**

- `last` 不存在；或
- `last.tool` 不同；或
- `last.status` 已经是 `done`/`error`（同 tool 再次 running 视为新的一次调用）

本轮真实情况：`rank_demand_lines` 出现两次、`resolve_inventory_access` 出现两次，因为第一次已经 `done`/`error`，第二次是新节点。这是正确行为。

### 2.3 节点稳定后的结构（前端内部态）

```ts
{
  id,                 // 前端生成：`${tool}-${eventIndex}`
  kind,               // "started" | "step"
  tool,               // started 节点为 "started"；其余为算法 tool 名
  title,              // 节点主文案，来自 title
  detail,             // 节点说明，空则不渲染该段
  status,             // running | done | error  → 左侧重绘图标
  source,             // 策略来源，见第 6 节
  preview,            // 结构化结果，见第 4 节
  thoughts[],         // 仅非 orchestrator 的 thinking
  stage,              // 过程字段，当前 UI 不画
  headline            // 过程字段，当前 UI 不画（与 title 重复）
}
```

## 3. 节点内字段：什么时候必须画、什么时候禁止画

节点模板固定四层，缺层就不渲染该层，不要用占位符。

```text
[状态图标]  title                          ← 必有
            tool（下划线改空格）            ← 必有
            [徽章…]                         ← 有可展示 preview/source 才有
            detail                          ← 非空才有
            [推理块]                        ← 该节点挂了非编排 thinking 才有
```

### 3.1 永远画在节点里（有节点就有）

| 字段 | 来源 | 呈现 | 算法要求 |
|---|---|---|---|
| `title` | `started.headline` 或 `step.title` | 节点主标题 | 给用户看的中文。running 用「正在…」，done 用「已…」，error 用「…未完成」 |
| `tool` | started 写死 `"started"`；step 用 `data.tool` | 标题下一行等宽小字，`_` → 空格 | 稳定英文蛇形名，前端不当标题 |
| `status` | step：`running`/`done`/`error`；started：前端记为 `done`（开跑事件本身已发生） | 只映射图标，不写英文。running=转圈，done=勾，error=叉；若 `status=done` 且 `source=fallback` 则勾改成警告三角 | 同一 tool 必须先 running 再 done/error |

### 3.2 有业务信息才画进节点（条件呈现）

下列字段**禁止**在 running 且尚无结果时画空徽章。`preview: {}`、`detail: ""`、`source: ""` 一律不占节点高度。

| 字段 | 出现条件 | 画在哪 | 文案映射 | 不画的情况 |
|---|---|---|---|---|
| `detail` | `typeof detail === "string" && detail.trim() !== ""` | 徽章下方正文 | 原文 | `""`、与 title 完全相同且无增量信息时算法应发 `""` |
| `preview.phase` | started 节点且非空 | 徽章「阶段 {phase}」 | 例：`阶段 MKE` | step 节点不要再带 phase |
| `preview.operatorType` | started 节点且非空 | 徽章 | `updateOrder` → **改单分配**；其余原样 | 空 |
| `preview.runId`（started） | started 节点 | 徽章，截断 `前8…后4` | 对账用 | step 的 `preview.runId` **不画**（与 started 重复） |
| `preview.taskCount` | number | 徽章「n 张任务」 | 含 0 | 非 number |
| `preview.poolCount` | number | 徽章「专用池 n」 | 含 0 | 非 number |
| `preview.unmetCount` | number | 徽章「缺口 n」 | 含 0 | 非 number |
| `preview.itemCount` | number | 徽章「加锁 n」 | 含 0 | 非 number |
| `preview.passed === true` | 严格 true | 徽章「校验通过」 | — | `false` 时不要画「校验通过」；失败靠 `status=error` + `detail` |
| `preview.submitted === true` | 严格 true | 徽章「已提交」 | — | false / 缺省 |
| `source` 或 `preview.source` | 见第 6 节 | 一枚徽章，**去重只画一次** | 见下表 | `""` |
| `preview.lineCount` / `waveOne` / `waveTwo` | number 且**至少有一个 ≠ 0** | 可画「需求行 n」「第一波 n」「第二波 n」 | 本轮全 0，当前实现**未画数字徽章**，回退信息走 `source` + `detail` | 全 0 不要堆三个 0 徽章 |
| `preview.module1Count` / `purchaseCount` | number | 建议徽章「模块一转交 n」「采购 n」 | 本轮为 0，当前实现未单独画，靠 `detail` 一句说完 | 已写进 detail 则可不再徽章 |
| `thoughts[].detail` | 该节点挂过非 orchestrator thinking | 节点内「推理」子块 | 见第 5 节 | 没有 thinking 就不建子块 |

`source` 徽章文案：

| 值 | 徽章 | 何时由算法发出 |
|---|---|---|
| `fallback` | **规则回退**（警告色）+ 节点图标改警告三角 | 主策略（通常是模型）不可用，改走规则，见第 6 节 |
| `default_policy` | 默认策略 | 本步从一开始就走默认规则，**没有尝试模型** |
| `none` | 无需加锁 | 仅 `propose_top_up`：评估后没有任何加锁项 |
| `""` | 不画 | running 或该步无策略概念 |

### 3.3 节点内明确不画（过程字段）

即使 payload 里有，**当前前端也不渲染到节点里**。算法仍应照发，供后端日志、排障、后续调试层使用。

| 字段 | 为什么不进节点 |
|---|---|
| `headline` | 本轮恒等于 `title`（started 上等于开跑标题） |
| `summary` | 本轮恒等于 `detail` 或 `title`，重复 |
| `stage` | 编排器状态机游标。后半段多步都是 `TOP_UP_DONE`，画出来会让用户以为还在加锁 |
| `preview.stage` | 与 `step.stage` 重复 |
| `preview.orderedTaskIds` | 内部任务 ID，无名称映射则对用户无意义 |
| `preview.module1Materials` | 明细数组；主界面只用数量或 detail 摘要 |
| `preview.errorCount` | 已被 `passed` + `detail` 覆盖 |
| `preview.runId`（submit 步） | 与 started 节点的 runId 重复 |
| `visible` | 过滤开关，不是文案 |
| `seq` | 编排心跳序号 |
| `event` / SSE id / 原始时间戳 | 协议信封 |

## 4. 只在运行过程中展示（完成后必须消失或改形态）

这些不是「节点的稳定正文」，而是**过程态**。

| 信息 | 数据来源 | 运行中怎么画 | 完成后 |
|---|---|---|---|
| 页头「规划中」+ 绿点 | 已收到 `started` 且未收到 `end` | 卡片顶栏 | 变为「已完成」+ 勾 |
| 已用时 `mm:ss` | 事件相对时钟 | 顶栏右侧，持续跳 | 停在最后一帧（本轮 00:47） |
| 当前 step 转圈 | `step.status=running` | 该节点左图标 | 被 done 勾 / error 叉 / fallback 三角替换 |
| running 标题「正在…」 | `step.title`（running 包） | 节点 title | **被 done/error 包的 title 覆盖**，节点上不再保留「正在」 |
| running 空 preview | `preview: {}` | 不画徽章层 | 被 done 包的 preview 替换 |
| 编排器心跳 | `thinking.role==="orchestrator"` 且 `status=running` | 时间线**最后一项**，独立「推理」条，文案用 `detail`（本轮为「正在规划本阶段库存分配。」），**不进入任何 step 节点** | `end` 到达后整条撤掉，不留历史 |
| 模型推理 running | `thinking.role!=="orchestrator"` 且 `status=running` | 挂到**当前 running 的 step 节点内**，正文闪动 | 同 role 的 done thinking **覆盖**该子块，闪动停止，**子块留在节点里**（这是决策依据，不是过程噪音） |

### 4.1 编排器 thinking 的特殊规则

本轮 `orchestrator` 在几乎每个 step 结束后都再发一条，字段长期不变：

```json
{ "role": "orchestrator", "title": "规划中", "status": "running", "detail": "正在规划本阶段库存分配。", "visible": true, "seq": 2 }
```

前端：

- 用最新一条覆盖内存中的 `orchestrator` 指针，**不累积**。
- 只在 `headerStatus==="running"` 时画在列表末尾。
- `title` / `headline` / `summary` / `seq` 不展示。
- 禁止因此新建节点，禁止插入到已完成 step 内部。

算法：这是心跳，不是新决策。不要把模型结论写进 `role=orchestrator`。

### 4.2 模型 thinking 挂载规则

`role !== "orchestrator"`（本轮为 `demand_lines.system`）：

1. 宿主 = 时间线上**从后往前第一个 `status=running` 的 step**；若没有 running，则挂到最后一个节点。
2. 同一 `role` 在同一宿主上只保留一条，后到覆盖先到（running 文案 → done 文案）。
3. 子块展示：标签「推理」+ `role` 原文 + 正文 `detail`（空则 fallback 到 `title`）。
4. 子块在宿主 done 之后**仍然保留**。

本轮两次模型推理：

| 时刻 | 宿主 step | running 正文 | done 正文 |
|---|---|---|---|
| t=5790→17232 | `rank_demand_lines`（第一次） | 模型会把关键件放进第一波、辅料放进第二波，可能需要几秒。 | 关键件P3优先于P4；辅料同波次内，高改单次数(P4)得分高于低改单(P3)，符合紧急分逻辑。 |
| t=22810→34335 | `plan_upstream` | 同上 running 文案 | 关键件Wave1，辅料Wave2。同物料内按紧急度排序：P3优于P4，P4中改单多者更急。 |

## 5. 各事件字段总表（生产者 → 消费者）

### 5.1 `started`

| 字段 | 生产者含义 | 前端 | 进节点？ |
|---|---|---|---|
| `headline` | 开跑标题 | 作为节点 `title` | 是，主标题 |
| `detail` | 开跑说明 | 节点正文 | 是，非空 |
| `summary` | 摘要 | 忽略 | 否 |
| `phase` | 规划阶段代码 | 徽章「阶段 MKE」 | 是 |
| `operatorType` | 触发类型 | 徽章，`updateOrder`→改单分配 | 是 |
| `runId` | 本轮 ID | 徽章截断 | 是（仅此节点） |

收到 `started` 后页头进入「规划中」。节点 `status` 直接 `done`（事件已发生，不是进行中的工具）。

### 5.2 `step`

| 字段 | 生产者含义 | 前端 | 进节点？ |
|---|---|---|---|
| `tool` | 工具名 | 次行 | 是 |
| `title` | 当前态中文 | 主标题，running/done 覆盖 | 是 |
| `status` | running/done/error | 图标 | 是（形态） |
| `detail` | 完成后的一句话 | 正文 | **仅非空** |
| `source` | 策略来源 | 徽章 + fallback 时改图标 | **仅非空** |
| `preview.*` | 结构化结果 | 按 3.2 白名单抽徽章 | **仅白名单且有值** |
| `headline`/`summary` | 重复文案 | 忽略 | 否 |
| `stage` | 状态机 | 忽略 | 否 |
| `visible` | 是否对用户可见 | false 则整条丢弃 | 否 |

`step.stage` 取值（过程，算法继续发，前端不画）：

`PREPARED` → `REQUIREMENTS_COMPUTED` → `TASKS_RANKED` → `ACCESS_RESOLVED` → `LINES_RANKED` → `PURCHASE_COMPUTED` → `TOP_UP_DONE`

注意：`propose_top_up` 完成之后，后续 `get_unmet_demands` / `validate_plan` / `submit_target_plan` 的 `stage` 都停在 `TOP_UP_DONE`。这表示「加锁阶段已结束」，不是这三步还在做 top-up。所以不能把 `stage` 当节点标签。

### 5.3 `thinking`

| 字段 | 生产者含义 | 前端 |
|---|---|---|
| `role` | `orchestrator` = 心跳；其它 = 模型/子系统 | 分流；模型 role 画在推理块次标签 |
| `status` | running / done | 闪动 vs 静态 |
| `detail` | 给用户的推理/心跳文案 | 唯一正文 |
| `title` | 短标题 | 仅 detail 为空时兜底 |
| `headline`/`summary`/`seq` | 重复或序号 | 不画 |
| `visible` | 开关 | false 丢弃 |

### 5.4 `result`（当前 UI 不建节点）

| 字段 | 含义 | 当前前端 |
|---|---|---|
| `code` / `message` | 协议成功（200 / success） | 不画 |
| `data.runId` | 与 started 重复 | 不画 |
| `data.actions` | 落库动作列表 | 不画（本轮 `[]`） |
| `data.unmetDemands` | 未满足需求 | 不画（本轮 `[]`） |
| `data.warnings[]` | 终态告警 | **不画**。回退已在对应 step 节点用 `source=fallback` + `detail` 表达 |

算法仍必须发 `result`：后端落库、对账、以后若要恢复结果区可以接上。`warnings[].code` 与 step 的 `source=fallback` 必须能对上（见第 6 节）。

### 5.5 `end`

| 字段 | 前端 |
|---|---|
| `status=COMPLETED` | 页头「已完成」，撤编排器心跳 |
| `eventCount` | 不画 |

## 6. 回退（fallback）——为什么会有、谁负责、怎么展示

### 6.1 三种「策略来源」不要混用

| source | 语义 | 用户该理解的事 | 本轮出现在 |
|---|---|---|---|
| `default_policy` | **没走模型**，直接规则 | 「按默认策略做的」 | `rank_tasks`、第一次成功的 `resolve_inventory_access` |
| `fallback` | **主策略失败后改走规则** | 「模型这次没被采用，用了规则，结果可能次优」 | 第一次 `rank_demand_lines` 的 done |
| `none` | 评估后无动作 | 「没有可加锁的剩余库存」 | `propose_top_up` |
| `error` 状态（不是 source） | 这一步没做完，编排器决定继续 | 「这步失败了，后面按规则往下」 | 第二次 `rank_demand_lines`、第二次 `resolve_inventory_access` |

`default_policy` ≠ `fallback`。  
前者是设计如此；后者是降级。前端徽章文案必须分开，算法不得把「本来就走规则」标成 `fallback`。

### 6.2 本轮回退的真实因果（算法侧）

`rank_demand_lines` 的主策略是大模型波次评估（`role=demand_lines.system`）。

时间线：

1. t=5789 `step running` → 节点出现「正在安排主料和辅料的抢货波次」，无徽章。
2. t=5790 `thinking running`（模型）→ 节点内出现推理闪动：「模型会把关键件放进第一波…」。
3. t=17232 `thinking done`（模型）→ 推理正文换成模型结论（P3 优先于 P4…）。**注意：模型文本成功了，不等于结构化结果被采纳。**
4. t=17234 `step done` + `source=fallback` + `preview: { source:"fallback", lineCount:0, waveOne:0, waveTwo:0 }` + `detail`「波次评估回退到规则策略，当前没有可排列的需求行。」
5. t=47726 `result.warnings` 出现：

```json
{
  "code": "LINE_RANKING_FALLBACK",
  "severity": "warning",
  "message": "主料辅料波次评估回退到规则策略，未使用模型排序结果。"
}
```

**原因拆开写给算法：**

- 模型产出了可读的紧急度解释（thinking.done.detail），但**没有产出可被执行器使用的波次结构**（或结构校验失败、空行）。
- `lineCount=0`：没有可排列的需求行，波次数字全 0。
- 执行器不能停在「只有一段自然语言」，必须继续分配库存，于是 **source 置 `fallback`**，改用规则策略（或空结果）往下走。
- 终态 `LINE_RANKING_FALLBACK` 是这条降级的正式告警码，供对账；当前 UI 不单独画 warning 列表，因为节点上已经有「规则回退」徽章 + detail。

之后 t=20063 再次 `rank_demand_lines running`，t=20068 `status=error`。这是**另一次调用失败**，不是 fallback。error 节点：叉图标 + title「安排主料辅料波次未完成」+ detail「这一步没有做完，系统会按规则继续…」。编排器仍继续 `plan_upstream`。

### 6.3 回退时算法必须同时给出的字段

`status=done` 且主策略未采用时，**缺一不可**：

| 字段 | 必填值 | 前端用它做什么 |
|---|---|---|
| `source` | `"fallback"` | 警告三角 + 「规则回退」徽章 |
| `preview.source` | `"fallback"`（可与 source 相同） | 与 source 去重，只画一次徽章 |
| `detail` | 人话原因，说明回退和后果 | 节点正文。本轮：「波次评估回退到规则策略，当前没有可排列的需求行。」 |
| `title` | 完成态标题，不要再写「正在」 | 「已安排主料和辅料波次」 |
| 对应 `result.warnings[]` | `code` 稳定、`message` 与 detail 同义 | 当前不画；后端落库；以后结果区可接 |

禁止：

- 只改 thinking 文案、step 仍 `source=""` —— 前端无法标警告。
- `source=fallback` 但 `detail=""` —— 用户只看到徽章不知道为什么。
- 把 fallback 标成 `error` —— error 表示步骤没做完；fallback 表示做完了但是降级成功。
- 把 `default_policy` 标成 `fallback`。

### 6.4 前端回退呈现（当前实现）

```text
status === "done" && source === "fallback"
  → 左图标 = 警告三角（不是绿勾）
  → 徽章「规则回退」（warning 色）
  → 若有 detail，原文展示
  → 若节点内有模型 thinking.done，推理块仍保留
     （用户能同时看到「模型怎么想的」和「实际没采用」）
```

这是有意的：回退不是把模型思考删掉，而是并列「想了什么 / 实际用了什么」。

## 8. 前端 reduce 伪代码（实现契约）

```
on event:
  if thinking|step and visible === false: return
  elapsed = event.t

  started:
    header = running
    push node { kind:started, tool:"started", title:headline, detail,
                status:done, preview:{runId,phase,operatorType} }

  thinking:
    if role === "orchestrator":
      orchestrator = {role,title,status,detail}   // 覆盖
      return
    host = last running step || last step
    upsert host.thoughts by role

  step:
    if last.tool===tool and last.status==="running":
      patch last {title,status,source,preview merge, detail if non-empty}
    else:
      push new node { kind:step, tool, title, status, source, preview, detail }

  result:
    store only

  end:
    header = completed
    orchestrator 不再渲染
```

## 9. 算法发包检查清单

1. 每个工具：**先** `status=running` 且 `preview={}`、`detail=""`、`source=""`，**再** 终态包。
2. running 的 `title` 用「正在…」；终态覆盖为「已…」或「…未完成」。
3. 用户可读结论写在终态 `detail`，不要只放在 `summary`/`headline`。
4. 结构化数字放 `preview` 白名单字段；内部 ID 放 `orderedTaskIds` 等，前端默认不画。
5. 走模型的步骤：running 时发 `thinking.role=<子系统>`；有结论再发 thinking.done；**无论模型文本是否成功，结构化是否采纳都要在 step.done 的 `source` 上说清楚**。
6. 降级：`source=fallback` + 非空 `detail` + `result.warnings` 带稳定 `code`。
7. 从一开始就走规则：`source=default_policy`，不要标 fallback。
8. 步骤失败但流水线继续：`status=error` + 说明「会按规则继续」的 `detail`，不要标成 fallback。
9. `visible=false` 仅用于调试/内部事件。
10. `stage` 继续发，供后端状态机；不要指望前端展示它。

## 10. 前端渲染检查清单

1. 不要为 thinking / result / end 建 step 节点。
2. 不要把 started 固定在表头，不要做底部结果栏。
3. `detail===""`、`preview=={}`、`source===""` 不占位。
4. orchestrator 心跳只在运行中出现在列表末尾，完成后删除。
5. 模型推理留在宿主节点内，done 后不删。
6. `source=fallback` 的 done 节点用警告形态，即使 HTTP/result 是 200。
7. `headline`/`summary`/`stage` 不渲染。
8. 同一 running 工具的第二条 step 是 patch，不是第二行。
